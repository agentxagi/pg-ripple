# v0.140.4 — Stable-SID Single-Row Upsert (VAL-377)

## Theme

Re-asserting an existing triple no longer mints a new SID nor rewrites the
VP delta row: the single-row upsert paths return the EXISTING statement ID
and leave the physical row version untouched.

## Problem

The dedicated-VP fast paths of `insert_triple()` /
`insert_encoded_triple()` (`src/storage/ops/mod.rs`) upserted with

```sql
INSERT INTO _pg_ripple.vp_{id}_delta (s, o, g) VALUES (...)
ON CONFLICT (s, o, g) DO UPDATE SET i = EXCLUDED.i
RETURNING i, (xmax = 0)
```

The `i` column's `DEFAULT nextval('statement_id_seq')` is evaluated for the
proposed row on **every** call, so each re-assert of an existing quad:

- minted a fresh sequence value and **returned a different SID** every time
  (641 → 642 → 643 observed while root-causing VAL-365 on `/opt/pg-ripple`
  0.140.0) — breaking any consumer that treats the SID as the stable
  identity of a row;
- **rewrote the conflicting row** (new tuple version per re-assert: WAL
  churn and bloat under the re-assert-heavy production load —
  `load-ripple.sh`, `backfill-ripple-sync.ts`, entity re-ingestion);
- fired the delta CDC/timeline triggers as an **UPDATE**, adding trigger
  noise on every engine re-assert pass.

Found during the VAL-371 delivery (PR agentxagi/pg-ripple#18 review, 04/10);
non-blocking for 0.140.1 because the engine ignores the returned SID — but
the rewrite cost and the unstable identity were real.

## Fix

- New `vp_delta_upsert()` helper (`src/storage/ops/mod.rs`) used by both
  fast paths: `ON CONFLICT (s, o, g) DO NOTHING` inside a CTE plus a
  `UNION ALL` arm that selects the EXISTING row — still one atomic
  statement, one roundtrip:
  - arm 1 returns fresh inserts only (`TRUE AS inserted`);
  - arm 2 returns the existing SID with `FALSE` — zero row rewrite, no
    UPDATE triggers.
- The VAL-371 contract is preserved: only real inserts bump
  `triple_count` / the shmem delta counters.
- Concurrent-commit race (another transaction commits the same quad while
  our INSERT waits on the conflict; the statement snapshot predates that
  commit so both arms miss): a fallback re-read with a fresh snapshot
  returns the committed SID — the race degrades to `(existing_sid, false)`
  instead of an error.

## Out of Scope (follow-up)

- Sequence gaps: `DO NOTHING` still evaluates the `nextval()` DEFAULT for
  the proposed row, so re-asserts consume sequence values (gaps only — no
  SID ever changes hands). Avoiding the evaluation would need dropping the
  DEFAULT from the insert column list; not worth the churn for gap-only
  cost.
- The batch paths (`copy_into_vp` / `batch_insert_encoded`) already use
  `ON CONFLICT DO NOTHING` (VAL-371) and have no rewrite problem.
