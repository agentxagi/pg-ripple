# v0.140.4 — Stable SID on Re-Assert (VAL-377)

Re-asserting an existing triple through the single-row delta upserts now
returns the row's EXISTING statement ID and leaves the physical row
untouched, instead of minting a fresh SID and rewriting the row on every
pass.

## Defect

`insert_triple` and `insert_encoded_triple` (`src/storage/ops/mod.rs`)
upserted into the dedicated VP delta table with:

```sql
INSERT INTO _pg_ripple.vp_{id}_delta (s, o, g) VALUES (...)
ON CONFLICT (s, o, g) DO UPDATE SET i = EXCLUDED.i
RETURNING i, (xmax = 0) AS inserted
```

`i` defaults to `nextval('_pg_ripple.statement_id_seq')`, so `EXCLUDED.i`
carried a fresh sequence value on every attempt: the conflict path OVERWROTE
the existing row's statement ID and physically rewrote the row each pass —
SID 641→642→643 observed over three re-asserts of the same triple (found
during the VAL-371 delivery review, PR agentxagi/pg-ripple#18, 04/10/2026).

Consequences:

- **SID was not a stable identity.** `pg_ripple.insert_triples()` hands
  statement IDs to SQL callers; any consumer treating the SID as the row's
  stable identity would break. (The ValorBrain engine ignores the return
  value today, so this was latent, not live.)
- **WAL/bloat churn for nothing.** Production re-asserts heavily
  (load-ripple.sh, backfill-ripple-sync.ts, entity re-ingest): every
  re-assert produced a new tuple version of an already-correct row.

## Fix (Rust only — no SQL objects change)

Both single-row upserts share `upsert_delta_row()`:

```sql
WITH ins AS (
    INSERT INTO _pg_ripple.vp_{id}_delta (s, o, g) VALUES ($1, $2, $3)
    ON CONFLICT (s, o, g) DO NOTHING
    RETURNING i, true AS inserted
)
SELECT i, inserted FROM ins
UNION ALL
SELECT d.i, false FROM _pg_ripple.vp_{id}_delta d
WHERE d.s = $1 AND d.o = $2 AND d.g = $3
  AND NOT EXISTS (SELECT 1 FROM ins)
LIMIT 1
```

- Fresh insert: the first arm returns `(new sid, inserted = true)`.
- Re-assert: the second arm returns the EXISTING row's SID with
  `inserted = false`; the physical row is never touched (no new tuple
  version, no WAL churn) and `i` keeps its original value — SIDs are now
  stable across re-asserts.
- The `inserted` flag preserves the VAL-371 counting rule: only real
  inserts bump `triple_count` / the shmem delta counters.
- The statement stays atomic (one round-trip, no SELECT-then-INSERT race).
  If a concurrent transaction commits the same triple between this
  statement's snapshot and its conflict wait, both arms return no row;
  pgrx surfaces that as `SpiError::InvalidPosition`, reported as a
  duplicate (SID 0) — the same convention `insert_into_vp_rare` already
  uses for its `ON CONFLICT DO NOTHING` path.
- `nextval()` is still evaluated for the attempted insert, so the sequence
  burns one value per re-assert (a harmless gap: SIDs stay unique, no row
  is written).

Callers were audited for the return-value change: `dict_api.rs`
(tabling/SHACL gating on `sid > 0`), `insert_triples()` (SetOf SIDs — now
stable instead of fresh-per-re-assert), `llm/mod.rs` and `rag.rs`
(`sid > 0` counting) — none regress; re-asserts keep returning a positive
SID.

## Verification

- New regression `tests/pg_regress/sql/v0144_sid_stable_reassert.sql`
  (hermetic for the shared regress database):
  - `insert_triple` (dictionary API): after promotion, 5 re-asserts of the
    same triple return the SAME SID, and the physical delta row's `i` AND
    `xmin` are unchanged (red on the previous `DO UPDATE` logic: both
    moved on every re-assert).
  - `insert_encoded_triple` (SPARQL UPDATE `INSERT DATA`): 3 re-executions
    leave the row's `i` and `xmin` unchanged.
  - Counter cross-check: per-predicate `triple_count` equals the distinct
    triple count after all re-asserts (VAL-371 invariant kept).
- A/B: suite re-run on the same cluster — no new failures vs. the base
  tree; `v0141_triple_count_reassert.sql` stays green (counting semantics
  unchanged).

## Upgrade

Version marker only: `ALTER EXTENSION pg_ripple UPDATE TO '0.140.4'`
(Rust-only fix; loading the new library binary requires the usual
PostgreSQL restart because pg_ripple is in `shared_preload_libraries`).
No data migration: existing rows keep their current `i` values.
