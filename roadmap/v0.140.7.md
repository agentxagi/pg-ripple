# v0.140.7 — HTAP Merge Race (MERGE-RACE-01)

The background HTAP merge destroyed rows that committed while a merge
cycle was running, and undid deletes that arrived in the same window.

## Defect

`storage::merge::merge_predicate` (`src/storage/merge.rs`) ran, in one
READ COMMITTED transaction:

1. `CREATE TABLE vp_{id}_main_new AS (main − tombstones) ∪ delta` — no
   lock on delta or tombstones (MERGE-FENCE-01 deliberately keeps this
   phase lock-free);
2. BRIN index build, then the per-predicate advisory lock and the
   rename-swap of `main`;
3. `TRUNCATE vp_{id}_delta`.

Every statement takes a fresh snapshot, so a row committed into delta
after step 1 and before step 3 was not in `main_new` but was removed by
the TRUNCATE: silent data loss. The insert paths
(`src/storage/ops/mod.rs`) take no part in the merge fence.

Tombstones had the same flaw. With the default
`pg_ripple.tombstone_retention_seconds = 0` the tombstones table was
TRUNCATEd too, so a delete that wrote its tombstone mid-merge was dropped
and the triple reappeared from `main_new`. The `retention > 0` branch
deleted `i <= max_sid_at_snapshot` (a `last_value` read of
`statement_id_seq` at merge start), which is unsound: sequences are not
transactional, so a tombstone whose SID was drawn before that read but
committed after `main_new`'s snapshot was deleted without being applied.

A third, smaller case: deleting a triple that lives in delta removes the
delta row and writes no tombstone. If that happened after step 1, the
triple was already copied into `main_new` and was resurrected.

Production evidence (2026-10-06 22:41:18–22): the merge worker rebuilt
`vp_1393_main_new` (`kg/related_to`) while a backfill inserted
`related_to` triples; a 40P01 deadlock was logged in the same window, and
78 freshly inserted `related_to` triples vanished (no row, no tombstone).

## Fix (Rust only — no SQL objects change)

- **Step 0:** snapshot delta (`s, o, g, i, source`) and tombstones
  (`s, o, g, i`) into private `ON COMMIT DROP` temp tables. `main_new`
  is built from these snapshots, so the merge knows exactly which rows it
  consumed.
- **Swap phase:** after the advisory lock, `LOCK TABLE delta, tombstones
  IN EXCLUSIVE MODE`. This waits for in-flight writers and blocks new
  writes until commit, while reads continue. It is weaker than the
  ACCESS EXCLUSIVE the old TRUNCATE took, and it is taken *before* `main`
  is renamed. Locking `main` first and delta second could deadlock with a
  writer that holds delta and then reads `main` (as `delete_triple`
  does).
- Under that lock, snapshotted delta rows that no longer exist in delta
  (deleted mid-merge) are removed from `main_new`.
- **Cleanup:** `DELETE … USING <snapshot>` on `(s, o, g, i)` for delta and
  for tombstones replaces both TRUNCATEs and the `max_sid` filter. Rows
  written during the merge stay for the next cycle, and the joins use the
  existing delta `UNIQUE (s, o, g)` and tombstones `(s, o, g)` indexes.
  Matching on the statement id `i` too means that a triple deleted and
  re-inserted mid-merge (new SID) is never confused with the consumed row.
- `triple_count` becomes `rows(main) + rows still in delta`, because each
  surviving delta row was already counted on insert. The delta bloom bit
  is cleared only when delta is really empty.

Why not "delete `i <= max SID at snapshot`" for delta: SIDs are drawn
from a non-transactional sequence, so a writer can hold a lower SID than
the captured horizon and still commit after the snapshot. `dedup` also
re-inserts survivors into delta with their *original* (old) SID.
Matching the exact snapshotted rows is correct under READ COMMITTED
regardless of commit order.

## Regression

The pg_tests in `src/storage/merge.rs` use the internal
`merge_predicate_with_hook`. Its hook runs after `main_new` is built and
before the swap, which is exactly the race window:

- `test_merge_keeps_delta_row_inserted_mid_merge`: an insert in the
  window survives, `triple_count` counts it, and the next merge folds it
  into `main`;
- `test_merge_keeps_tombstone_written_mid_merge`: a delete of a
  main-resident triple in the window stays deleted across two merges;
- `test_merge_drops_delta_row_deleted_mid_merge`: a delete of a
  delta-resident triple in the window is not resurrected.

## Known limits

- `erase_subject()` (`src/security_api.rs`) deletes directly from
  `vp_{id}_main`. An erase that commits while a merge is building
  `main_new` can still be undone by the swap. This is pre-existing and out
  of scope here.
- `delete_triple` takes `pg_advisory_xact_lock_shared(p_id)`, while the
  swap phase locks `0x5052_5000 + p_id` (CC13-02). The keys only collide
  through the worker's session lock on `p_id`, which is taken only when
  `merge_workers > 1`, so that fence did not cover the single-worker
  default or `compact()`. The table lock above now gives the guarantee
  independently of the advisory keys.
