# v0.140.6 — Erasure Completeness (VAL-378)

Follow-up of the [v0.140.3](v0.140.3.md) delete-side counter fix (PR #20):
`erase_subject()` removed the erased subject's dictionary entry while rows
referencing the id as an **object** (or graph) were left behind — the
mirror image of the same incomplete-delete family.

## Defect

`security_api::erase_subject_impl` (`src/security_api.rs`) deleted rows
with `s = <erased id>` from `vp_rare` and every dedicated VP delta/main
table, then deleted the subject's dictionary entry **unconditionally**
(the code comment admitted skipping the cross-reference check "for
performance"). Consequences:

1. rows with `o = <erased id>` or `g = <erased id>` survived with an id
   that no longer resolved in `_pg_ripple.dictionary`;
2. every SPARQL result decoding such a row emitted
   `WARNING: batch_decode: dictionary entry missing for id N` and bound
   the value to an empty string (graceful degradation,
   `pg_ripple.strict_dictionary = off`; with strict mode on it would be a
   PT512 error);
3. the erased id lived on in the HTAP pattern caches
   (`object_patterns`/`subject_patterns`) and in the unlogged
   `dictionary_hot` encode cache — a stale hot entry would return the
   deleted id on a future insert of the same IRI, silently re-creating
   the orphan;
4. if `named_graphs` ever registered the erased IRI as a graph, the
   registry row survived the erase.

Production evidence (ValorBrain KG, tenant graph `b49feee2…`): id 60581,
referenced by exactly one `vp_{1393}_main` row (`s=40402`, `o=60581`,
`g=7826`, predicate `kg/related_to`) plus one `object_patterns` row; a
full-KG orphan scan (1.9M live ids across `vp_rare`, 12 VP views and the
catalog) found **60581 was the only orphan**. First WARNING occurrence
2026-09-28 04:13:58 (`/var/log/postgresql/postgresql-18-main.log.6.gz`);
re-seen five times during the 0.140.1 deploy verification
(04/10 11:22:01–11:27:32). `pg_ripple.strict_dictionary` is `off` in
production, so impact was bounded to noisy logs and empty bindings — but
the id gap around it (60580/60583) is unreferenced sequence drift, not
corruption, confirmed by the same scan.

## Fix (Rust only — no SQL objects change)

`erase_subject_impl` now matches the erased id in **every role**:

- `vp_rare`: `DELETE … WHERE s = $1 OR o = $1 OR g = $1`, still grouping
  the removed rows per predicate for the VAL-376 counter decrement;
- every dedicated VP `delta`/`main` table: same three-role predicate;
- `subject_patterns` (`s = $1`) and `object_patterns` (`o = $1`): the
  star-pattern cache rows keyed by the erased id;
- `named_graphs` (`graph_id = $1`): the registry row when the IRI was
  used as a graph;
- `dictionary_hot` (`id = $1`, best-effort — the table is created
  lazily): evicts the id from the unlogged encode cache so a future
  insert of the same IRI mints a fresh dictionary entry instead of
  re-using the deleted id.

The dictionary-entry delete stays unconditional — after the deletes
above, nothing references the id anymore.

## Test

`tests/pg_regress/sql/v0146_erase_subject_object_refs.sql` loads a graph
where the erased subject also appears as the object of another subject's
triple, captures the dictionary id before the erase, and asserts: the
object-referencing triple is physically gone (0 rows, not an
empty-binding row), no `vp_rare` row references the id in any role, the
pattern/hot caches hold no residue, the predicate counter is back to 0
(VAL-376 invariant), the dictionary entry is gone, and the other
subject's triples are untouched. On the unfixed build the same script
reproduces the production signature exactly —
`WARNING: batch_decode: dictionary entry missing for id 2`,
`orphan_refs_after = 1`, `knows_after = 1`.

## Production repair (operator step, not part of this PR)

The pre-existing orphan is two rows: `vp_{1393}_main (40402, 60581, 7826)`
and `object_patterns (o=60581)`. Removing them with the matching
`triple_count` decrement (VAL-376 pattern) completes the original erase;
re-running the full-KG orphan scan afterwards must return an empty set.
The WARNING is benign meanwhile (`strict_dictionary = off`).
