# v0.140.1 — Catalog Counter Integrity (VAL-371)

## Theme

Every insert path now increments `_pg_ripple.predicates.triple_count` only for
**real** inserts: duplicates absorbed by `ON CONFLICT` / `NOT EXISTS` no longer
inflate the catalog counter. Fixes the root cause of the VAL-365 catalog drift.

## Problem

On 0.140.0 all insert paths in `src/storage/ops/mod.rs` bumped the per-
predicate counter unconditionally while the SQL absorbed duplicates:

- `insert_triple` / `insert_encoded_triple` single-row upsert fast paths did
  `+1` per call even when `ON CONFLICT (s, o, g) DO UPDATE` returned the
  EXISTING statement id;
- `batch_insert_encoded` added `rows.len()` (the requested count) on top of
  `INSERT … ON CONFLICT DO NOTHING` — VP-delta branch (VALUES and
  UNNEST/`bulk_load_use_copy` sub-paths) and the `NOT EXISTS`-guarded vp_rare
  branch;
- the Citus direct-shard batch path had the same defect per shard.

Measured in production on 0.140.0 (04/10/2026):
`pg_ripple.triple_count()` 647.255 vs 624.116 physical/visible rows
(**+23.139**), concentrated in `rdf:type`, `kg/entityType`, `kg/name`,
`related_to`, `depends_on`, `caused_by` + 529 on the vp_rare path — every
workload that re-asserts triples (`load-ripple.sh`, `backfill-ripple-sync.ts`,
entity re-ingestion) inflated the counter on each pass. Deletes were already
correct; the leak was entirely on the insert side.

## Fix

- Single-row upserts: `RETURNING i, (xmax = 0)` — only a fresh row (xmax = 0)
  counts; the conflict path (existing row updated) does not.
- Batch paths: `WITH ins AS (INSERT … ON CONFLICT DO NOTHING RETURNING 1)
  SELECT count(*)` — the same shape already used by Datalog materialisation
  (`seminaive.rs`) and SPARQL `ADD`.
- `copy_into_vp` (UNNEST/bulk-load COPY path) returns the real inserted count.
- Citus direct-shard path: same per-shard real-insert counting.
- Shared-memory delta counters (`record_delta_inserts`) record the real delta.

No SQL objects change: `sql/pg_ripple--0.140.0--0.140.1.sql` is a version
marker so `ALTER EXTENSION pg_ripple UPDATE TO '0.140.1'` can walk the
release. The production counters converge via a one-shot recompute in the
deploy window, not by this migration.

## Out of Scope (follow-up)

- The single-row upserts keep `DO UPDATE SET i = EXCLUDED.i` with `i`
  defaulting to `nextval()`, so re-asserting a base triple returns a new SID
  and rewrites the row (observed churn). The engine ignores the returned SID
  today; tracked as a follow-up issue.
- The one-shot counter recompute in the deploy window can re-drift over time
  if a delete-side counter gap exists (delete_triple is correct, but
  clear/drop-graph paths are separate code); validate before the window or
  schedule periodic recompute in the runbook.
