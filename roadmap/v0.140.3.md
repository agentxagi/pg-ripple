# v0.140.3 — Delete-Side Catalog Counter Fix (VAL-376)

Companion of the [v0.140.1](v0.140.1.md) insert-side fix: every mass-cleanup
path that removed `vp_rare` rows now decrements
`_pg_ripple.predicates.triple_count` by the rows it actually removes.

## Defect

`storage::clear_graph_by_id` and `storage::drop_graph`
(`src/storage/ops/scan.rs`) maintained counters correctly for dedicated VP
tables but their `vp_rare` half deleted rows (`DELETE ... RETURNING p`) and
only summed the count for the return value — the catalog never heard about
the removal. `security_api::erase_subject` (GDPR erase) and the physical
branches of `storage::ops::dedup` had the same gap.

Consequences:

- `SPARQL CLEAR GRAPH` / `CLEAR ALL` / `DROP GRAPH`, `pg_ripple.drop_graph`
  and `erase_subject` on graphs holding rare predicates (below the
  promotion threshold) leaked `triple_count` upward.
- The next re-assert of the same triple counted as a **real** insert (the
  `NOT EXISTS` guard finds nothing), re-drifting catalog above physical —
  after the VAL-371 one-shot recompute, production would re-drift on every
  graph cleanup. Bisected: `w3c_sparql_update_conformance`'s wholesale CLEAR
  wipes `vp_rare`; re-running `v0141_triple_count_reassert.sql` then moves
  its p3 counter 1 → 2 while the physical count stays at 1 (VAL-371
  validation finding, 04/10/2026).
- The A/B full-suite run exposed a fourth path of the same class:
  `execute_add_by_ids`'s `vp_rare` branch (`src/sparql/execute/update.rs`) —
  SPARQL `ADD` into a rare predicate inserted rows silently (no counter
  bump). With the delete side fixed, `MOVE`/`COPY` decrement a cleared
  source graph that the ADD phase had never incremented, leaving
  counter-0-with-rows orphans that armed `vacuum_vp_rare`'s broken
  non-volatile `DELETE` (surfaced as a `v062_features` failure).

## Fix (Rust only — no SQL objects change)

- `clear_graph_by_id` / `drop_graph` vp_rare branches: delete + per-predicate
  decrement in one statement —
  `WITH d AS (DELETE FROM _pg_ripple.vp_rare WHERE g = $1 RETURNING p), agg
  AS (SELECT p, count(*) FROM d GROUP BY p), upd AS (UPDATE
  _pg_ripple.predicates SET triple_count = GREATEST(0, triple_count - agg.cnt)
  ...) SELECT sum(...)` — same defensive `GREATEST(0, ...)` shape as every
  other decrement path.
- `erase_subject`: per-table decrement for `vp_rare` (aggregated by
  predicate), `vp_*_delta` and `vp_*_main`.
- `deduplicate_predicate`: decrements by the physical duplicates removed
  from delta and vp_rare.
- `execute_add_by_ids`'s `vp_rare` branch: increments by its real inserts,
  same shape as the dedicated-VP branch.

## Verification

- New regression `tests/pg_regress/sql/v0143_triple_count_delete_sides.sql`
  (hermetic for the shared regress database): CLEAR GRAPH on a rare
  predicate zeroes the counter; re-loading returns it to the exact distinct
  count; `drop_graph` API, a promoted-predicate clear control (no
  double-decrement) and `erase_subject` coverage; namespace-scoped
  catalog == physical invariant.
- Original v0141 symptom: full suite in a shared database, then re-running
  `v0141_triple_count_reassert.sql` — p3 counter stays at 1 with the
  physical row intact (was 1 → 2 on 0.140.2 logic).

## Upgrade

Version marker only: `ALTER EXTENSION pg_ripple UPDATE TO '0.140.3'`
(Rust-only fix; counters converge via the existing VAL-371 recompute or the
nightly kg-drift guard).
