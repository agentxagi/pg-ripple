# v0.140.5 — Dedup Main-Branch Tombstone Maintenance (VAL-380)

Follow-up of the [v0.140.3](v0.140.3.md) delete-side counter fix (PR #20):
the dedicated-tables (main) branch of `deduplicate_predicate` tombstoned
duplicate `(s, o, g)` groups but never told the catalog or the HTAP view.

## Defect

`storage::ops::dedup::deduplicate_predicate` (`src/storage/ops/dedup.rs`),
main-table branch, on finding duplicate `(s, o, g)` rows in `vp_{id}_main`:

1. never updated `_pg_ripple.predicates.tombstone_count`;
2. never rebuilt the HTAP view when it was in the tombstone-skip form (no
   `LEFT JOIN`), so the new tombstones stayed invisible until some other
   path (delete, clear, merge) rebuilt the view;
3. re-runs re-inserted one tombstone per duplicate group — the tombstones
   table has no unique constraint, so the `ON CONFLICT DO NOTHING` guard was
   inert — and re-counted the same duplicates on every call;
4. and, decisively: **one tombstone masks every main row of the group**
   (the tombstone join is on `(s, o, g)`), including the minimum-SID row
   that must survive. Once any path put the view in the tombstone-aware
   form, a deduplicated group with no delta row vanished from reads, and
   the next merge dropped it permanently — `find_triples` lost the triple
   immediately, `main` ended at N−1 groups, and catalog versus physical
   drifted.

## Fix (Rust only — no SQL objects change)

The main branch of `deduplicate_predicate` now runs one statement that:

- tombstones each duplicate group **once** — the `INSERT` is guarded by
  `NOT EXISTS` on the tombstones table, so repeated runs are no-ops and a
  pre-existing tombstone (a real delete, or a prior dedup run) always wins
  over re-asserting a survivor;
- re-asserts the group's minimum-SID row into `vp_{id}_delta` (explicit
  `i`, `ON CONFLICT (s, o, g) DO NOTHING`), so the tombstone-aware view
  keeps returning the triple and the next merge collapses `main` to
  exactly one physical row — the behaviour the function's documentation
  always claimed ("duplicates are masked at query time and removed on the
  next merge");
- returns the number of rows beyond the survivor for newly tombstoned
  groups (a group of N rows removes N−1), and decrements
  `triple_count` by that amount — the same contract #20 gave the
  delta/vp_rare branches, keeping catalog, query visibility and physical
  in lockstep at every point;
- recomputes `tombstone_count` absolutely from the tombstones table and
  flips the view to the tombstone-aware form when the count leaves 0 —
  the M15-05 contract every other tombstone writer already honours.

Delta survivors get the standard insert bookkeeping (`record_delta_inserts`,
delta bloom bit) so reads and the next `compact()`/merge see them.

## Regression

`tests/pg_regress/sql/v0145_dedup_main_tombstones.sql` (hermetic, v0143
pattern): promotes a predicate with 100 distinct triples, creates a physical
duplicate in `main` (re-assert + merge), then asserts — red on the #20 base,
green here — that dedup

- returns 1 and makes `tombstone_count` equal the tombstones table (base:
  stayed 0);
- puts the HTAP view in the tombstone-aware form immediately (base: stayed
  in tombstone-skip form);
- keeps the triple queryable via the delta survivor, with `triple_count`
  decremented to 100 (base: kept 101 and lost the triple);
- is idempotent (base: returned 1 again and doubled the tombstone row);
- collapses `main` to 100 rows on the next merge with no data loss (base:
  ended at 99 and drifted the scoped catalog-vs-physical invariant).

## Drive-by: `drop_graph` dedicated branch (same defect class)

The test's cleanup section exposed a fifth path of the same class:
`storage::drop_graph`'s dedicated branch tombstoned the graph's main rows
but, unlike its sibling `clear_graph_by_id`, never updated
`tombstone_count` nor rebuilt the view — so `DROP GRAPH` on a promoted
predicate left the dropped rows served by the tombstone-skip view until
some other path rebuilt it (the test asserts catalog 0 vs SPARQL 100 on
the base). It now gets the same M15-05 block: absolute `tombstone_count`
recompute + view flip when the count leaves 0.
